# yomiyasu — GameAI Hub用

[nanaism/yomiyasu](https://github.com/nanaism/yomiyasu)を基にしたリポジトリ限定の静的スキルです。
上流の固定版、変更点、ライセンスは[UPSTREAM.md](UPSTREAM.md)と[LICENSE](LICENSE)を参照してください。
インストールコマンド、外部サービス、APIキーは不要です。

## 適用範囲

「この導入を読みやすく」「この節だけyomiyasuで推敲して」など、対象が明示された依頼で使います。
最初にルートのAGENTS.md、記事ならapp/articles/AGENTS.md、および
docs/agent-guides/OWNER_DIRECTED_OPERATIONS.mdを読み、対象ファイル・節・元のSHAを記録します。
このスキルは現在の依頼とリポジトリの保護規則を補助するもので、優先しません。

全文・全記事・サイト全体が明示的な依頼範囲なら、その範囲を棚卸しして適用します。依頼されていない実ファイルの書き換えや、文脈を無視した自動置換はしません。
比較案の依頼なら比較案だけを作り、公開記事へ反映しません。
Acceptance、監査、承認、実行証跡、過去の比較原文、進捗記録は推敲対象にしません。
他のスキルやアカウント設定を無効化する必要はありません。

## 保持するもの

- 主張、比重、断定・推量・可能性の強さ、文の働き、条件・否定・含み。
- 動作主・動作・対象・時期、修飾先・参照先、例外・限定・数量とそれぞれがかかる範囲。
- 事実、数値、単位、料金、日付、モデル名、引用、URL、コード、コマンド、識別子。
- 不明・未確認・非決定的・結果を保証しない等の確度と制約。推敲を新しい事実検証と扱わない。
- アフィリエイト／プロモーション開示、リンク属性、計測、SEOメタデータと確認日。
- 判断に必要な箇条書き、手順の順番、比較表、対応表、注意事項と失敗時の手順。

これらを文体のために削除・追加・強調変更しません。文脈で分からない主語、機能、原因を補いません。
事実の修正が必要に見えた場合は別の確認事項として報告します。元のunknownはunknownのままです。

## 推敲の進め方

1. 原文と周辺の文脈を読み、文書全体の用件、各段落が伝える内容、上記の保持項目を確認します。
   見出し・導入・箇条書き・結びの対応も確かめ、不明な関係を推測でつなぎません。
2. 指す先が明らかな代名詞だけを具体化し、誰が何をするかを読み取りやすくします。
   主体や対象を補うのは、原文や提供文脈から対象と関係が確定する場合だけです。
   複数の読みがある修飾先を一つに決めず、動詞を替えた後も元の対応を確かめます。
3. 不自然な擬人化や比喩を、元の意味の範囲で普通の言葉に戻します。正当な専門用語や慣用句は残します。
4. 重複する前置きは、主張と比重を保てる場合だけ整理します。評価や誤解の訂正を担う否定は残します。
   長い文は、目的・手段・理由・条件・順序・対比と、それぞれがかかる範囲を維持できる場合だけ分けます。
   文長だけを理由に分けず、「何のために何をするか」の向きが変わるなら原文を残します。
5. 装飾や空白は読解を妨げる箇所だけ整えます。コードやタグの空白・記号は変えません。
   英単語や数値の前後の空白を一律に削除・追加せず、原文や指定の書式を保ちます。
   読みやすい読点は数だけで削らず、句点ごとの改行や空行の一律追加もしません。
6. 原文と修正案を照合し、保持項目の欠落、強さの変化、事実の追加がないか確認します。
   意味が変わりそうな箇所は原文を残して指摘します。修正試行は最大2回を目安とします。

見聞きした時期と出来事が起きた時期を区別し、現在の動作・方針、完了した変更、今後の予定を入れ替えません。
常体・敬体は変更指定がなければ原文を保ち、技術記事という理由だけで敬体にしません。

上流の文長30〜45文字、読点0〜2個、箇条書き15%以下などは本リポジトリの必須条件ではありません。
重要な一覧を文章化したり、数値目標だけを満たすために文章を崩したりしません。
score 100、警告ゼロ、定量的な文体比率を要求しません。CIや公開判定のゲートにも追加しません。

## 情報と文末を増やさない

箇条書きを文章にするときも、元にない評価（「大切です」）や義務（「必要があります」）を足しません。
並列の項目は箇条書きのまま残せます。文末の反復を減らすために項目を結合し、理由の範囲や比重を変えません。
道具や仕組みの客観的な説明（「このツールはログを集めます」）は擬人化として直しません。
「このツールを使えばログを集められます」のように、元にない条件や可能性を足しません。
言い切った説明を「できます」に変えたり、曖昧な語を根拠なく狭い技術的な事実へ置き換えたりしません。

不自然な直訳を定着した専門用語へ直すのは、原文や提供文脈から専門的な対象と意味が確定する場合だけです。
実名、UI項目名・部品ラベル、識別子、日常語の意味、値と判定条件は保ち、型や仕組みを推測で補いません。
提供された定義や値と状態の対応は説明に活かせますが、未知の情報は作りません。

文末は、依頼の読み手・用途と原文の手がかりから、説明・勧め・決まりのどの立場かを確認します。
立場と強さを保持し、明確に合わない箇所だけを対象範囲内で整えます。文書全体を一律の文末にしません。
手順を順に述べる「まず〜します。次に〜します」や、仕組み・書き手の予定を説明する「します」は残します。
原文でそろった文末、説明の最後だけにある勧め、原則の説明に続く手順を、単に混在や反復として直しません。
「しましょう」を「してください」「しなければなりません」に強めるなど、勧め・依頼・義務を入れ替えません。
立場、接続先、目的や理由の範囲が不明なら原文を維持し、書き手への確認事項として提示します。
文末や接続を変えた場合は、原文との差と理由を出力に記します。

## Markdownの太字

Markdownとして描画する対象範囲で、残す太字の区切りが文字として表示される場合だけ書き方を整えます。
かっこは太字の外に出して内側の語を強調し、末尾の句点も太字の外へ出します。
それで直せない場合は、文字に接する区切りの外側に半角スペースを入れ、描画を確認します。
表示に必要な空白は削除せず、語句・意味・強調の比重を変えません。太字を新たに増やす指示ではありません。
この対策をTSX、JSXのstrong要素、コード、コードフェンス内の原文に機械適用しません。
表示環境が不明なら一括置換せず、原文を残して確認します。

## TSX記事の扱い

記事はMarkdownではなくTSXです。上流リンターはMarkdown向けの簡易検査で、コードやHTMLなどの
保護範囲を検査項目ごとに扱います。TSXを直接渡しても、JSX式や読者に見える文章全体を正しく
解析する保証はありません。高得点でも読みやすさや意味保持の証拠ではありません。

固定版v2.0.0のPython標準ライブラリだけで動くlint / diff / checkと参照資料を同梱しています。
実行コードとライセンスの確認結果はUPSTREAM.mdを参照してください。フック、インストーラー、外部通信、モデル、CIゲートは追加しません。

## v2.0.0の検査手順

1. 原稿を変える前に原文を保存します。記事は`references/doc-types/article.md`、操作案内は`manual.md`、
   紹介文は`promo.md`、技術説明は`references/domains/tech.md`も読みます。種類・読者・立場を確定できない場合は指定しません。
   `references/rephrase-test.md`の観点で主題、肯定・否定、動作主・対象、範囲・条件、確度、数値・名称・時期を比較します。
   補助動詞と形式名詞の表記は整えますが、それ以外の表記揺れは機械的に統一しません。
2. `python3 .agents/skills/yomiyasu/scripts/yomiyasu_lint.py 原文.md`で候補を確認し、原文の全体も読みます。
   候補ゼロも未修正も合格の意味ではありません。`references/review-points.md`を参照し、文脈に合う用語、重要な否定、一覧は残します。
3. 最終稿を保存し、CLIから次を実行します。状態には原文・最終稿が含まれます。秘密情報を入れません。

   ```bash
   python3 .agents/skills/yomiyasu/scripts/yomiyasu_check.py run --source 原文.md --final 最終稿.md --state-dir /tmp/yomiyasu-state --fact-gaps
   python3 .agents/skills/yomiyasu/scripts/yomiyasu_check.py verify --final 最終稿.md --state-dir /tmp/yomiyasu-state
   ```

4. runが最後まで実行されたことと、verifyのハッシュ一致を確認します。修正したらrunとverifyを再実行します。
   未変更の稿にも実行します。最終稿のlintとdiffを個別実行してcheckの代わりにしません。
   点数・候補数・実行記録は意味保持、理解、品質、承認の証明ではありません。独立レビューと既存の受入検査は別に行います。
5. TSXはコードを直接検査せず、見える文章・属性・メタ説明・データ文言をパスと位置に対応づけたプレーンテキストへ抽出します。
   `scripts/editorial-copy-inventory.mjs`は日本語の文字列・JSXテキスト・テンプレート断片を拾う候補棚卸しです。
   内部用文字列や引用も含み、式の補間、表示条件、英語だけのUI、文字列の連結はソースと画面で確認します。
   ソースへの書き戻しは行いません。検査後に最終ソースから再抽出し、検査した稿とバイト単位で一致させます。
   引用・過去ログは検査に含まれても書き換えません。抽出の完了を全画面の表示確認と混同しません。

検査の状態、保持した表現、残った意味差、実行しなかった検査を正確に報告します。資料から値を補う手順は
`references/fact-recovery.md`にありますが、今回のような意味保持の推敲では新しい事実を追加しません。

## 出力と承認

元のSHA・パス・範囲、原文、修正案、変更理由、保持確認、未解決の意味差を短く提示します。
読者向け本文と編集側の理由・質問を分け、本文に「要確認」などの編集注記を挿入しません。
原文の未定・調査中の状態や条件付きの主張は本文に残し、推敲側の迷いを原文の不確実性に置き換えたり、
言い切った主張を伝聞や批評へ変えたりしません。理由や質問でも未知の主体・原因・関係を決めつけません。
「本文のみ」の指定があれば、SHA・範囲・保持確認などは内部で記録し、理由・質問を添えず本文だけを返します。
通常の比較出力ではリンター未実行ならその旨を記し、手作業の推敲をリンター生成結果や独立した受入判定と呼びません。
本文への反映が別途承認されたら、ページと記事レジストリの整合性を保ち、既存の品質検査と必要な表示確認を行います。
マージはオーナーの別途承認が必要です。自動マージ、デプロイ、旧Workトリガーを起動しません。
